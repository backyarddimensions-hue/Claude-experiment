4. `cli.doHealthCheck` makes an outbound HTTP GET (`internal/cli/health_check.go:22`).

**Policy guess was wrong, main causes:**

- `entry_tombstones` accounts for 28 of the 48 hits. I did not know the table existed. It is consulted inside the INSERT in `storage.createEntry`, so
  every package that can create a feed inherits `reads entry_tombstones`. A storage-internal
  bookkeeping table leaks into the noun list of six packages.
- `cli` accounts for another 13: it runs migrations, so it writes every table including
  dropped ones, and it runs refresh jobs that read `integrations`. Should be `nouns: *`.
- `worker` is not interior; its job is to trigger network fetches.

**Analysis over-approximation:**

- `opml.Import` is inferred to write `entries` and `enclosures`. It calls `storage.CreateFeed`
  with a feed that has no entries, so that loop never runs. The analysis is flow-insensitive.
- `http/server.setupAutocert` is marked `net` because the sink table treats every
  `autocert.Manager` method as a network call.

**Clean result:** no package outside `internal/storage` and `internal/database` executes SQL
directly. On that axis the code matches the declaration exactly.

## Condition B: proposed prompt and tools (draft, not built)

### What B sees before its first tool call

1. The task text (same wording as condition A).
2. The file list: every non-test `.go` path, with line counts. No contents.
3. Every `.agentpolicy` file, inline (about 40 files of 3 lines).
4. A signature index, one line per function, grouped by package:
   `[effects] signature  // file:line`. Exported functions show their declared tag.
5. A description of the three tools.

Not inline: graph.json. At 1.8 MB it does not fit; B queries it through a tool.

### Tools

| Tool | Returns | Counted as |
|---|---|---|
| `graph(function_id)` | That function's graph.json entry | 1 round trip; response tokens count toward input |
| `open_file(path, start_line, end_line)` | The requested lines | 1 file open (distinct files tracked), lines read |
| `edit(path, old_text, new_text)` and `create_file(path, content)` | ok or error | 1 round trip |
| `finish()` | Ends the run; the harness takes `git diff` as the submitted diff | |

No shell, no grep, no directory listing, no test runner. Run with `claude -p`,
`--model claude-fable-5-2`, stream-json output for token and tool accounting, user settings and
plugins disabled so nothing from this machine leaks in.

### Draft prompt

```
You are making one change to a Go codebase. You cannot browse it freely.

You have been given: the task, the list of files, every function signature with its effect
tag, the policy file for each package, and a tool to query the call graph.

Effect tags: pure | reads <table> | writes <table> | net | fs | mut. A tag lists everything the
function does directly or through anything it calls. Policy files state which tables a package
may touch, its priority, and its boundary role.

Tools:
- graph(function_id): callers, callees, effects and source position of one function.
- open_file(path, start_line, end_line): read part of a file. Every call is logged. Open only
  what you need in order to write a correct change.
- edit(path, old_text, new_text), create_file(path, content): make the change.
- finish(): submit.

Work out where the change belongs from the signatures, tags and graph first. Then open the
bodies you must see, make the change, and call finish.

Task: <task text>
```

### Decisions I need from you before building it

1. **Unexported functions in the signature index.** The design says exported signatures only.
   In Miniflux `internal/api` has 64 functions of which 1 is exported, and `internal/ui` has 142
   of which 6 are. Every HTTP handler is an unexported method. With exported-only, B's first view
   of the API package is one line (`Serve`), and task 6 cannot start without opening files. My
   recommendation: include unexported named functions with their inferred effects, exclude
   anonymous closures. That is about 1,300 lines.
2. **Edits instead of raw diffs.** The design says B submits a diff. Hand-written unified diffs
   fail on hunk arithmetic for reasons unrelated to the hypothesis. I propose `edit` plus
   `git diff` taken by the harness. The submitted artifact is still a diff.
3. **Test feedback.** Condition A with a normal harness has a shell and can run `go build` and the
   tests, then iterate. B as designed cannot. Left as is, a correctness gap could be caused by
   feedback rather than by legibility. Options: (a) give B a `check()` tool that returns compiler
   and test output, counted; (b) remove the shell from A and give both the same `check()`;
   (c) keep the asymmetry and accept the confound. I recommend (b): identical feedback, only
   read access differs.
4. **Which tree A runs on.** The tags are comments in the source, so A sees them if it runs on
   `annotated`. I recommend both conditions run on `annotated`, so the only variable is access.
   The alternative (A on the untagged tree) tests "layer plus restriction" against "neither".
5. **Whether refresh counts for task 6** (path 7 in the ground truth). See that file.
